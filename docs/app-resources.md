# Per-app resources

Overview reports Docker CPU consumption in cores and RAM working set (usage minus reclaimable inactive file cache), each app's actual configured CPU/RAM ceilings and measured peaks. No limit means shared host capacity; ceilings do not reserve exclusive resources. Measurements are sampled once per minute, so very short bursts between samples can be missed. Missing or stale data is unavailable, never zero.

Owned Plex and container apps use the paired HTTPS Agent. MediaSeed and MediaVPN use their approved local Compose installation. Other integrations explain why control is unavailable. Shared provider, gateway and relay containers appear once in a separate read-only row. MediaSeed counts its running torrent client once while retaining the stopped Compose template for recreation. Limits are split between MediaSeed app/client (25/75 percent) and MediaVPN app/proxy (80/20 percent); the displayed app ceiling is their sum, not a shared cgroup pool. A component's configured share remains its own ceiling.

Administrator edits are available on Overview and in app settings. RAM changes require at least 20 percent headroom above the current working set of every affected component. Increases are checked against the Docker host and other running containers, keeping ten percent RAM for the host. CPU affinity and memory reservations are preserved. Existing Docker NanoCPU caps can be adjusted live but cannot be removed through Docker update; the UI explains that removing such a cap requires container recreation.

History keeps five-minute peaks for fourteen days and separates installations and allocations. Increasing requires at least ten recent buckets spanning 45 minutes, with three buckets reaching 90 percent of the ceiling. Reducing requires seven days with at least 80 percent coverage, an average at most five percent and a peak at most ten percent. Missing intervals do not count as idle usage. Suggested changes never apply automatically; approval checks the current proposal, opt-out, ownership revision, capacity and live measurements again.

Resource recommendations can be switched off separately in each app's settings. Manual editing stays available and existing history is retained. Repeated notifications are deduplicated for one day. Successful edits resolve the old notification and start history for the new allocation.

Fresh installations and supported upgrades create the SQLite history/preferences database and operation journal automatically. Existing limits and configuration remain intact. Local limits are saved to persistent Compose configuration and installation-scoped state; approved installation recipes and Agent container creation reapply them when containers are recreated. MediaVPN 0.2.15 or later is required to inherit torrent-client limits after reconnects. Existing MediaVPN versions update separately from Core, and the UI explains this prerequisite. No VPN profile or credential migration is needed.

Changes are journaled, persisted before live application, verified and rolled back on failure, including a lost Docker acknowledgement. After a restart, an unfinished operation is verified without replaying the mutation. Uncertain recovery is shown explicitly and blocks changes to other apps until the affected app is reviewed and saved manually.

Validation uses synthetic Docker/Compose fixtures, API authorization/CSRF checks, persistent history/upgrade fixtures and isolated Chromium UI checks. It does not substitute for live Docker-host validation of kernel resource accounting or workload behavior.

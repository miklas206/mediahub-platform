# Overview host resources

CPU and RAM summarize the local Docker host, not the Core container. On Proxmox this is the containing LXC, including Core, installed apps, shared VPN services, and operating-system overhead. Remote Agents and other Proxmox guests are excluded. System disk is separate from configured media storage. Its capacity comes from statfs of a read-only host OS metadata-file bind, so the sampler does not need the host root directory or Docker socket.

The existing Core metrics contract remains intact; `host` is an additive optional observation. A small network-isolated, read-only sampler using the installed Core image reads host-provided proc and cgroup files every three seconds. It writes only its dedicated snapshot directory. CPU uses the parent cgroup counter with cpuset/quota capacity, falling back to Linux proc counters on a native host. RAM uses parent charged memory minus file cache. Core obtains capacity from the existing local Docker daemon connection every 15 seconds (two-second request bound), additionally respecting a finite parent cgroup limit. LXCFS virtualizes even bind-mounted meminfo for the reader, so the sampler cannot use MemTotal as host capacity. This fixes the observed 2.4 GiB / 64 MiB result while preserving the sampler's own 64 MiB limit and network isolation. Missing or invalid capacity yields unavailable telemetry. Older sampler snapshots are corrected on read; no manual server repair is required.

The installer and the existing startup prerequisite helper call the same idempotent provisioner. The helper receives read-only host telemetry mounts, creates or updates only the separately owned sampler Compose project, and never rebuilds or recreates Core, MediaSeed or MediaVPN for this operation. The sampler follows the installed Core image on subsequent Core updates. Hosts without readable proc/cgroup files show concrete prerequisite text. Snapshots expire after 15 seconds and failed readings never become zero usage.

App samples remain approximately once per minute (plus collection duration), with UI refresh every 15 seconds. Core samples normally publish every three seconds. The manual app Refresh button reads the latest server observation; it does not force another Docker sample. App RAM subtracts total file cache when provided by Docker (cgroup v2 file, v1 total_cache/cache), retaining the prior inactive-file fallback for older telemetry. Charged memory remains available internally. Peaks are historical, and total app usage need not equal the whole host because kernel services and cache charging differ. Accounting version is included in history selection so previously inflated peaks do not carry over; settings and raw historical records are preserved.

Validation includes native Linux and LXC fixtures, fresh/existing provisioning, stale snapshot handling, active file-cache regression tests, history version isolation, and Overview render checks. The sampler algorithm was executed read-only against the real LXC and compared with the Proxmox status API. The new sampler container has not been deployed or timed live.


## Local infrastructure attribution

Overview excludes remote hosts and adapters that only monitor external integrations, including Cloudflare Tunnel. Registered local Agent apps and owned managed Compose apps remain visible. Core/Agent/proxy/sampler have a separate read-only infrastructure group. VPN provider, gateways, port lease workers and app routing are grouped once by immutable container ID, with named component measurements. App frontend/proxy and torrent client containers are excluded from infrastructure groups even if they also carry owner labels. Parent usage includes kernel/OS overhead and measurements occur at different instants, so component totals need not equal host usage exactly.

## Healthcheck cleanup savings

The helper records one filesystem free-space observation before cleanup and one per status report afterward, exposing `freeBytesBefore`, `freeBytes`, signed `freeBytesChange` and nonnegative `reclaimedBytes`. These are a net filesystem observation, not summed image sizes (which can share layers); concurrent disk activity can influence it. The UI formats B/KiB/MiB/GiB/TiB, including zero and small savings, in the completion popup and operation details. The last result remains visible after reloading. A missing measurement is explicitly unavailable, not assumed zero. Cleanup retains its existing owned-file/image scope; media, app data, active/rollback images, Docker volumes and build cache are preserved.

Validation: 183 relevant Python tests and 14 frontend tests passed, with additional focused shutdown/prerequisite checks passing. Desktop/390/320 browser previews verified four distinct summary cards, a warning for low system disk space, expandable local infrastructure components, cleanup units and no horizontal overflow or page errors. The host OS-file filesystem probe was also read through the existing Core bind and returned the LXC system filesystem (about 31.2 GiB total). the RAM correction was evaluated inside the real Core container against a 0.6.35 snapshot and Docker daemon capacity, yielding about 2.51 GiB / 16 GiB versus Proxmox 2.50 GiB / 16 GiB. No deployed code or running service was changed by that read-only probe. Seven unrelated app-list performance tests also fail unchanged at baseline 48e3df7; the baseline checkout is retained under 2026-10-15/overview-036-baseline. No real cleanup or fresh-container launch was performed during validation.
